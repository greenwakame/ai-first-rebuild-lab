# 開発の進め方

このプロジェクトの最大の特徴は、対象領域そのものよりも**開発の進め方**にあります。

## この進め方はどこから来たか

いきなり5つの原則が並んでいるように見えますが、そうではありません。

このプロジェクトは、社内で続いてきた技術ワークショップの新しい題材として発足しました（[経緯](../README.md#なぜこのプロジェクトが始まったか)）。そのワークショップが教えてきたのは **「設計を先に固め、レビューを通してから実装する」** という順序です。以下の原則は、**その順序をAIエージェントが実装する環境で成り立たせるための具体策**です。

| 柱 | 要点 | 継承した考え方 |
| --- | --- | --- |
| [**AI-first開発**](#ai-first開発) | 共通指示を1か所へ集約し、繰り返す手順をskillへ切り出す | 実装者が変わっても手順が変わらないようにする |
| [**ADR駆動**](#adr駆動) | 元に戻しにくい判断は必ず記録する | **設計書レビューの後継**。判断を先に固め、記録に残す |
| [**契約優先**](#契約優先) | OpenAPIを正とし、CIで乖離を検出する | 設計と実装の乖離を人の注意力に頼らず検出する |
| [**要求トレーサビリティ**](#要求トレーサビリティ) | 受け入れ条件にIDを与え、仕様とコードのズレを終了コードで検出する | **完了条件の合意を、レビュー時の記憶ではなく機械に保持させる** |
| [**検証文化**](#検証文化) | 生成されただけでは完了ではない | **実装者が人からエージェントへ移った分、検証の比重が上がる** |
| [**供給網の扱い**](#供給網の扱い) | skillもhookも実行可能な攻撃面として扱う | エージェントに強い実行権限を渡す構成への対応 |

> [!IMPORTANT]
> **「設計を先に固める」規律がないままAIエージェントに実装させると、生成された差分を評価する基準がありません。** この順序を持っていることが、AI-first開発の前提になります。

## AI-first開発

このプロジェクトは、AIコーディングエージェント（Claude Code、Codex）による実装を前提に設計されています。人が毎回同じ説明を繰り返さずに済むよう、共通指示を1か所に集約する構造を採っています。

| 仕組み | 内容 |
| --- | --- |
| **`AGENTS.md`** | エージェントへの共通指示の唯一のソース。ミッション、リポジトリ境界、アーキテクチャ境界、作業手順、データ・セキュリティ方針、検証基準、コードレビュー基準を集約。実物は [reference/agents-md.md](reference/agents-md.md) |
| **`.agents/skills/`** | 繰り返し行う手順を切り出したもの。Issue駆動の実装フロー、PRの検査、マイグレーション管理、機能スライスの計画、セキュリティレビュー、UI検証。紹介は [reference/skills.md](reference/skills.md) |
| **アダプタ構造** | Claude Code と Codex の両方に対応。どちらのエージェントを使っても同じ`AGENTS.md`・同じskillsを参照する |

> [!IMPORTANT]
> AIが生成した差分をそのまま信頼するのではなく、**生成された差分を人が検証する**ことを前提にしたプロセス設計にしています。

## ADR駆動

**これは設計書レビュー文化の後継にあたります。** 実装より前に判断を固め、レビューを通し、記録に残す — 形式が設計書からADRへ変わっただけで、順序は同じです。

元に戻しにくい判断は、必ずADR（Architecture Decision Record）として記録します。「なぜその設計にしたか」を後から追えるようにすることが目的です。

- コンテキスト（何が問題か）、決定（何を選んだか）、その根拠を1つの文書にまとめます
- 判断が改訂された場合は、元のADRに改訂履歴を追記し、新しいADRとの相互参照を残します
- 実績として20件以上のADRを記録しています。実物は [adr/](adr/) を参照してください

ADRは、このプロジェクトの技術的な議論の質を最も直接的に示す資料だと考えています。

## 契約優先

Rust APIとNext.jsの境界はOpenAPIドキュメントを正とし、そこから型を自動生成し、CIで契約とコードの乖離を検査します。詳細は [architecture.md](architecture.md) を参照してください。

## 要求トレーサビリティ

契約優先がAPIの境界に対して行っていることを、**仕様と実装の間**でも行います。仕様の受け入れ条件に機械可読なIDを与え、実装とテストへマーカーで結び、ズレを終了コードで検出します。

| 仕組み | 内容 |
| --- | --- |
| **二系列のID** | `REQ-<領域>-<連番>` が仕様の受け入れ条件、`ADR-<番号>-D<n>` がADRの決定。前者は変化し続けるためドリフト検出の対象、後者は改訂履歴で追う対象として、性質ごとに分けています |
| **`@req` マーカー** | 実装とテストの該当箇所に1行置き、仕様 → 台帳 → コードを貫通させます。GitHub Issue番号とは分離し、Issueは台帳で関連付けるだけにしています |
| **共変更の検査** | 仕様だけが変わってコードが動いていない状態を検出します（error）。実装だけが変わってテストも仕様も動いていない状態は警告に留めます |
| **後退の検査** | 状態を「実装済み」から下げる、要求の種別を弱いほうへ移す — いずれも検出結果を消せてしまうため、後退そのものを検出対象にしています |

> [!IMPORTANT]
> **ズレを検出したら、エージェントは整合を取らずに停止して人へ報告します。** 検出スクリプトに `--fix` に相当する機能はありません。
>
> 生成AIが仕様とコードの両方を書く体制では、**「仕様のほうを書き換えて辻褄を合わせる」「状態を下げて警告を黙らせる」が最も起こりやすい失敗モード**です。この仕組みは、それを検出するために存在します。整合させる判断は人に残します。

**既存コードから要求を逆生成しません。** 実装の挙動を要求文へ書き換えたものは、定義上コードと常に一致するためズレを検出できません。さらに一度IDを持つと、次以降のセッションはそれを人が決めた事項として読みます。逆生成した要求は現時点で0件です。

検出できないものも規約に書いています。**同じPull Requestで仕様とコードを同時に書き換えれば、検査は通過します。** 検出しているのは共変更規約の違反であって、散文の要求とコードの意味的な一致ではありません。1つのIssueを1つの縦切りに保つ、という運用がこの仕組みの前提です。

現在は警告のみで運用し、観測結果を見てからブロックへ切り替える段階導入にしています。判断の経緯と却下した4案は [ADR 0023](adr/0023-requirement-traceability-and-drift-detection.md)、運用規約の実物は [reference/requirements-md.md](reference/requirements-md.md) にあります。

## 検証文化

> [!NOTE]
> **「コードが生成されただけでは、タスクは完了していない」** — この原則を運用に落とし込んでいます。

| 原則 | 内容 |
| --- | --- |
| **未実行のチェックを合格と言わない** | 現在のworktreeで実行に成功していないチェックを、合格したと主張しない |
| **低いレイヤーで検証する** | テストは意味のある最も低いレイヤーで行い、ユーザーに見える振る舞いにはサービス横断・E2Eのカバレッジを追加する |
| **値を見ずに移行を検証する** | マイグレーションでは、スキーマ・行数・キー関係・代表的なチェックサムを比較する（実データの値は露出しない） |
| **UIの状態を網羅する** | loading・空状態・エラー・権限拒否・狭い画面幅の状態を確認する |
| **できなかったことを書く** | 必要なチェックが実行できない場合は、具体的な障害要因を説明し、再現可能な次のコマンドを残す |
| **仕様とのズレを検査する** | Pull Requestを出す前に `mise run req:check` を通し、仕様・コード・テストのどれか一方だけが動いていないかを確認する（[要求トレーサビリティ](#要求トレーサビリティ)） |

日常のコマンド実行は `mise run <task>` に集約しており、「手元でこのコマンドが通った」という事実だけを根拠に完了を主張する運用にしています。

## 供給網の扱い

skills、hooks、MCPサーバー、CIワークフロー、依存関係スクリプトは、いずれも**実行可能な攻撃面**として扱います。有効化する前に、実行内容と認証情報のスコープをレビューします。

AIエージェントに強い実行権限を与える構成である以上、通常のコードレビュー以上に供給網のレビューを重視する必要がある、という判断によります。
