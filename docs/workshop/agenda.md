## 3. 環境構築

事前準備（[prerequisites.md](prerequisites.md)）が済んでいる前提で、次を実行します。

リポジトリを取得します。Windows 11 + WSL2 の場合は、Windows側（`/mnt/c/` 配下）ではなく
`~/src` などWSL2側のディレクトリで実行してください。

```bash
git clone <招待されたリポジトリのURL>
```

cloneしたディレクトリへ移動してから、以降を実行します。

**macOSのみ**、共通CLIとAI開発アプリを導入します。WSL2ではHomebrewを使わず、
事前準備で導入したUbuntuのツールをそのまま使います。

```bash
brew bundle
```

```bash
brew bundle --file Brewfile.macos
```

ここからは**両環境共通**です。リポジトリが固定するツールと、プロジェクトの依存を導入します。

```bash
mise install
```

```bash
mise run install
```

ツールと外部接続を確認します。

```bash
mise run doctor
```

```bash
mise run doctor:external
```

両方が通れば環境構築は完了です。`doctor:external` はGitHub認証とDocker daemonを確認します。
Docker Desktopの起動直後は準備に時間がかかるため、失敗した場合は起動の完了を待って
再実行してください。

> [!WARNING]
> ここでつまずいた場合はサポートしますが、**事前準備を済ませてきていただくことが最大の時間短縮になります。**

## 4. Issue選定

当日取り組めるIssueを用意しておきます。その中から、興味のある領域・使いたい言語に合わせて選んでください。

| 観点 | 内容 |
| --- | --- |
| **領域** | Next.js（UI）、Rust（API）、PostgreSQL（スキーマ・認可）、ドキュメント。**用意できる領域は開催回によって変わります** |
| **規模** | 1日で着手からPR提出まで到達できるもの |

> [!IMPORTANT]
> 選んだIssueについて、着手前に**何を達成すれば完了なのか**を合意します。これはこのプロジェクトの進め方の中核です。**Issueの完了条件が曖昧なまま実装を始めません。**

### 当日のIssueは採番済みの要求に限定します

このプロジェクトでは、仕様の受け入れ条件に `REQ-<領域>-<番号>` という識別子を振り、実装・テストと対応づけています（[requirements-md.md](../reference/requirements-md.md)）。

**当日お渡しするIssueは、この番号が既に振られているものに限定します。** 番号のないコードを変更すると `mise run req:check` が差分を検出して停止し、「要求を先に書いて採番する」という、当日の時間内では決めきれない判断が必要になるためです。

番号のある要求から始めることで、Issueの完了条件・実装・テスト・Pull Requestの記載が最初から対応します。

## 5. 実装

AIコーディングエージェント（Claude Code / Codex）を使って実装します。

このプロジェクトでは、エージェントへの共通指示を `AGENTS.md` に集約し、繰り返す手順を `.agents/skills/` へ切り出しています（[agents-md.md](../reference/agents-md.md) / [skills.md](../reference/skills.md)）。エージェントはこれらを読んだ上で作業します。

> [!IMPORTANT]
> **重要な点は、生成された差分を自分で読んで検証することです。** 「エージェントが書いたから正しい」とは扱いません。

## 6. 検証

実装したら、リポジトリの検証コマンドを実行します。

```bash
mise run check
```

担当した要求と実装・テストが対応しているかを確認します。

```bash
mise run req:check
```

UIを変更した場合は、加えて次を実行します。

```bash
mise run check:ui
```

「現在のworktreeで実行に成功していないチェックを、合格したと主張しない」という原則があります。**通らなかったものは通らなかったと記録します。**

> [!TIP]
> `mise run req:check` が要求のずれ（drift）を報告した場合は、**その場で止めて相談してください。** 仕様を書き換えて検出を消すのではなく、何がずれているのかを一緒に確認します。この検出は、まさにそれを見つけるためにあります。

## 7. Pull Request の提出

日本語でPull Requestを書きます。テンプレートが用意されているので、次の欄を埋めます。

- [x] 何を変更したか
- [x] 対象要求（担当した `REQ-...` の識別子）
- [x] どの検証を実行し、何が成功したか
- [x] **確認できなかったことは何か**

> [!NOTE]
> 最後の項目を省略しないことが、このプロジェクトのPRの特徴です。実際の例は [issue-walkthrough.md](issue-walkthrough.md) を参照してください。

## 8. レビュー

提出されたPull Requestを、その場でレビューします。設計判断の背景、検証の考え方、なぜこの粒度でIssueを切るのかといった観点を共有します。

マージは当日中とは限りません。レビュー内容によっては追加の修正をお願いすることがあります。
