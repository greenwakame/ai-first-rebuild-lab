# Issue着手からマージまでの実例

実際にクローズされたIssueを1件取り上げ、着手からマージまでの流れを再現します。当日みなさんが行う作業のイメージをつかむための資料です。

題材にするのは、メンバー一覧画面の**検索フォームの整列と、一覧アバターの拡大**という表示改善です。規模としては7ファイル・118行追加/68行削除で、半日で着手からPR提出まで到達できる典型的な大きさです。

> [!NOTE]
> このIssueとPull Requestは開発用のprivateリポジトリにあるため、リンクは掲載していません。内容は実物から転記しています。

---

## 1. Issue

### タイトル

> メンバー検索フォームの整列と一覧アバターの視認性を改善する

ラベルは `type:feature` / `area:web` / `priority:medium`、マイルストーンは「Phase 4: 最初の縦切り」。担当者を設定してから着手します。

### Issue本文の構造

このプロジェクトのIssueは、次の8項目で構成します。

| 項目 | 何を書くか |
| --- | --- |
| 目的 | 何を達成するか。1〜2文 |
| 背景 | なぜ今それが必要か。**観測された事実**を書く |
| 設計決定 | どう作るか。実装前に決めておく |
| 対象範囲 | どこを触るか |
| 対象外 | どこを触らないか |
| 完了条件 | 何が満たされたら完了か |
| 検証 | どうやって確かめるか |
| リスクと復旧 | 何が壊れうるか、どう戻すか |

### 実物からの抜粋

**目的**

> メンバー一覧の実画面レビューで確認した検索フォームの縦位置ずれを構造的に解消し、社員を識別しやすい大きさへ一覧アバターを拡大する。

**背景**

> 2026-08-02の手動レビューで、氏名・氏名カナ欄だけが補助説明を含むため、form全体の `lg:items-end` によって当該欄のラベルと入力欄が上へ押し上げられ、並び順・方向・操作ボタンと揃わないことを確認した。また、一覧アバターは狭幅56px、640px以上64pxであり、人物中心の一覧として視認性が不足している。

ここで注目してほしいのは、**「なんとなく見た目が悪い」ではなく、崩れの原因（`lg:items-end` と補助説明の有無）まで特定してから書いている**点です。原因が特定されているので、後続の「設計決定」で対処方法を先に決められます。

**設計決定（抜粋）**

> - 1024px以上では12列gridを維持し、検索語5列、並び順2列、方向2列、操作3列とする
> - desktopの縦構造をラベル行、control・操作行、検索語の補助説明行の3行として明示する
> - 1024px未満はDOM順の1列を基本とし、氏名label、input、補助説明、並び順label、select、方向label、select、検索、リセットの順で表示する
> - `aria-describedby` によるinputと補助説明の関連、native label、検索からリセットまでのTab順を維持する
> - **invisible spacer、補助説明の複製、absolute positioning、負margin、任意pxのoffset、Tailwind arbitrary valueで位置を合わせない**

最後の1行が重要です。「見た目だけ合わせる回避策」を**あらかじめ禁止**しています。実装者（人間でもAIエージェントでも）が安易な手段に流れることを、着手前に塞いでいます。

**対象外**

> - Rust API、Storage契約の変更
> - プロフィール詳細画面の画像寸法変更
> - 実在社員写真やlegacy個人データの追加
> - 検索、sort、cursor、認証・認可仕様の変更

表示改善のIssueで認証・認可やAPI契約を触らないことを明示しています。スコープが膨らむのを防ぐと同時に、レビュー時に「触ってはいけないものを触っていないか」を確認しやすくなります。

**完了条件（抜粋）**

> - 1280px、1440px、1920pxで3つのlabel上辺と3つのcontrol上辺が視覚的に揃う
> - 360pxで自然なDOM順を保ち、横overflow、control欠け、読めない折返しがない
> - keyboardの順序が検索語、並び順、方向、検索、リセットとなり、focus ringが見える
> - avatarが狭幅64px、通常80pxで表示され、実画像、placeholder、画像失敗、loadingで同じ寸法になる
> - loading、empty、error、permission deniedの既存状態を壊さない

具体的な数値と状態が並んでいます。「きれいに整列する」ではなく「1280px / 1440px / 1920pxで上辺が揃う」と書くので、完了したかどうかを後から誰でも判定できます。

**リスクと復旧**

> 表示専用の変更であり、DB・API・認証境界への影響は想定しない。（中略）問題があれば検索form、MemberPhoto、loading、design policyの差分をまとめてrevertし、（前のPR）時点の表示へ戻す。

## 2. ブランチ

Issue番号を含む名前で、最新の `main` から作成します。

```bash
git switch -c claude/89-member-list-layout origin/main
```

命名規則は `<エージェント>/<Issue番号>-<スラッグ>` です。`<エージェント>` は、そのブランチを作った時点の主担当エージェント（`claude` または `codex`）を表します。

**Issueを作らずにブランチを切って、後からIssueを紐づけることはしません。** 計画の単位を常にIssueに置くためです。

## 3. 実装

このIssueで変更したのは7ファイル、118行追加・68行削除でした。

| ファイル | 変更内容 |
| --- | --- |
| `member-directory.tsx` | 検索フォームのgrid配置（64行変更） |
| `member-directory.test.tsx` | 整列とDOM順のテスト追加（46行追加） |
| `member-list-view.tsx` / `.test.tsx` | アバター寸法の変更とテスト |
| `member-loading.tsx` / `.test.tsx` | loading skeletonの寸法をアバターに合わせる |
| `frontend-design-policy.md` | 設計ドキュメントのアバター基準を改訂 |

注目してほしい点が2つあります。

**その1: 実装と同時にテストを書いています。** 3つのコンポーネントすべてにテストを追加・更新しています。「後でテストを書く」ではなく、同じPull Requestに含めます。

**その2: 設計ドキュメントも同じPull Requestで更新しています。** アバターの基準寸法を変えたので、それを記録している `frontend-design-policy.md` も同時に直します。コードとドキュメントが食い違った状態を残しません。

実装は「設計決定」で禁止した手段（invisible spacer、absolute positioning、負margin等）を使わず、grid上の行・列指定だけで解決しました。DOM順も変更していないため、キーボード操作の順序は自動的に維持されます。

## 4. 検証

ここがこのプロジェクトで最も特徴的な部分です。実行したのは次の5つで、**すべて作業中のworktreeで実際に実行して成功を確認**しています。

```bash
mise run check
```

lint、typecheck、format、TypeScriptテスト133件、Rustテスト56件、Next.jsビルド、Rustビルドをまとめて実行します。

```bash
mise run check:ui
```

デザイントークンの逸脱（許可していないCSSの書き方が混ざっていないか）を検査します。

```bash
mise run review:web:visual
```

Playwrightで19画面のスクリーンショットを生成し、axe-coreでアクセシビリティを検査します。この回は違反0件でした。

加えて、生成されたスクリーンショットを実際に見て、次を確認しています。

- 1280px / 1440px / 1920px で、3つのラベル上辺・3つのコントロール上辺・検索/リセットが同じ行に揃うこと
- 360pxで自然なDOM順の1列表示になり、横スクロールが発生しないこと
- 空状態・権限拒否・エラー・検索中の各状態でもフォームの整列が崩れないこと
- アバターの直径を画像解析で実測し、1280px幅で80px、360px幅で64pxになっていること

### 確認できなかったことを書く

Pull Requestには「確認できなかった事項」という節があり、実物では次の3点が記録されていました。

> - 「さらに表示」を実際にクリックして重複・欠落なく追記される挙動: 手動レビュー環境は対話ターミナルを必須とする設計（生成パスワードを非対話で読み取れないようにする意図的なゲート）のため、エージェントからは非対話実行できず失敗した。この挙動自体は既存のユニットテストで担保されているが、実ブラウザでのクリック操作は未確認。
> - keyboard Tab移動時の実際のfocus ring視認性: DOM順がTab順と一致することはユニットテストで確認したが、実際の見え方は目視未確認。
> - `prefers-reduced-motion` 適用時に実際にアニメーションが停止しているかの動的確認: 静的スクリーンショットでは判定不可。

**これを書くことが、このプロジェクトの規律です。** 検証できなかった項目を黙って省略すると、レビュアーは「全部確認済み」と誤解します。何が未確認かを明示すれば、レビュアーはそこを重点的に見られます。

「AIエージェントが実装した」という前提に立つと、この項目の重要性はさらに上がります。エージェントは指示されたことを実行しますが、**実行できなかったことを自己申告しなければ、誰も気づけません。**

## 5. Pull Request

日本語で書き、本文に `Closes #89` を含めます。これによりマージ時にIssueが自動でクローズされます。

構成は次の通りです。

- **概要**: `Closes #89` と、何を解決したか
- **変更内容**: ファイルごとに何をどう変えたか
- **対象外**: Issueの「対象外」と対応させ、触っていないことを明示
- **検証**: 実行したコマンドと結果、実画面で確認した内容
- **確認できなかった事項**: 上記の通り
- **復旧**: 問題があった場合の戻し方

Pull RequestはIssueのメタデータ（担当者・ラベル・マイルストーン）を自動で引き継がないため、専用のコマンドで同期し、同期結果を読み直してから「レビュー可能」とします。

```bash
mise run github:pr:sync-metadata -- 89 93
```

## 6. レビューとマージ

このPull Requestは指摘なくマージされました（レビューコメントの記録は0件）。

ただし、これは「レビューが省略された」という意味ではありません。**マージ操作は必ず人間が行います。** エージェントは自分の作ったPull Requestをマージしません。Issueの完了条件と、PR本文に書かれた検証結果・未確認事項を人が読んだ上で、マージの判断をします。

マージ後、`Closes #89` によってIssueは自動的にクローズされました。

## この実例のあとに増えた手順

> [!NOTE]
> **この記録は当時のIssueとPull Requestをそのまま転記したものです。** その後に進め方が1つ増えたため、現在の流れとの差分をここに書きます。実例の側を後から書き換えることはしません。

現在は、仕様の受け入れ条件に要求ID（`REQ-...`）を付け、実装とテストの該当箇所へマーカーで結んでいます。これに伴い次が変わりました。

| 節 | 現在の流れ |
| --- | --- |
| 1. Issue | 「対象要求」「影響範囲」の節が加わりました。着手前に、どの受け入れ条件を満たすのかをIDで明示します |
| 4. 検証 | `mise run req:check` が加わりました。仕様・コード・テストのどれか一方だけが変更されていないかを検査します |
| 5. Pull Request | 「対象要求」「影響範囲」の節が加わりました |

この実例の当時は、どれも存在しませんでした。判断の経緯は [ADR 0023](../adr/0023-requirement-traceability-and-drift-detection.md)、運用規約は [reference/requirements-md.md](../reference/requirements-md.md) にあります。
