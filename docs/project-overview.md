# プロジェクト概要

かつて社内で利用していた業務システムを題材に、ゼロから設計し直しています。対象領域はメンバー管理を中心に、経歴・スキル、現場・案件、面談、人事考課、権限管理まで広がる、いわゆる基幹寄りの業務システムです。

> [!IMPORTANT]
> **このプロジェクトはワークショップでの活用を主な目的にしています。** 実務に近い題材で、設計判断・認可設計・データ移行・検証といった開発プロセスを実際に体験してもらうことを狙いにしています。
>
> 社内で続いてきた技術ワークショップの**新しい題材**として発足しました。その経緯は [なぜこのプロジェクトが始まったか](../README.md#なぜこのプロジェクトが始まったか) を参照してください。**このページで説明する「なぜ作り直すか」は、そのうえで採った移行方針の話です。**

旧システムは単一ページアプリケーションのフロントエンドと、サーバーサイドAPI、リレーショナルデータベースを中心に構成されています。これを Next.js / Rust / Supabase を中心とした構成へ、段階的に置き換えています。技術スタックの詳細は [architecture.md](architecture.md) を参照してください。

## なぜ作り直すか

一括で書き直すのではなく、**機能単位の縦切り**で移行しています。理由は次の3つです。

| 制約 | 内容 |
| --- | --- |
| **テストがない** | 旧システムには自動テストがほとんど存在せず、既存挙動を保証する基準がありません。挙動の同等性を機能ごとに個別に検証しながら進める必要があります |
| **認可が独自モデル** | 「管理者/一般」のような単純なロールモデルではなく、グループ・ユーザー単位の例外を組み合わせた、機能・操作単位の確認を必要とするモデルです。安易にロールへ縮約すると権限漏れが起きます |
| **手順が再現できない** | 起動・デプロイに必要な設定の一部が構成管理の外にあり、クリーンチェックアウトだけでは旧システムの手順を再現できません |

これらの制約から、「大きく作り直して一度に切り替える」方式は採らず、検証可能な最小単位で機能を移行し、各段階で旧システムとの結果差分を説明できる状態を維持する方針にしています。詳しい進め方は [development-approach.md](development-approach.md) を参照してください。

## 難しさ

このプロジェクトが技術的に歯応えがあると考えている点です。

| 論点 | なぜ難しいか |
| --- | --- |
| **認可モデルの移行** | グループ・ユーザー単位の例外を含む独自の認可モデルを、データベースの制約とクエリレベルの絞り込みとして再現する必要があります。アプリケーション層の判定だけに頼らない設計を重視しています |
| **データ移行の検証** | 自動テストがほとんど存在しない旧システムに対して、行数・チェックサム・キー関係の突合など、**値そのものを見ずに**移行の正しさを検証する方法を設計する必要があります |
| **保証基準がない状態からのテスト設計** | 「今まで動いていたから正しい」という前提が使えないため、機能ごとに期待される挙動を明文化してからテストを書く必要があります |

## 扱うデータ

> [!NOTE]
> **開発で使うのは合成データだけです。** メンバー名や写真なども、この用途のために作った架空のデータです。参加にあたって機密情報の取り扱いを心配する必要はありません。

実在する人物の情報や、実際に運用されていたデータをローカル環境やCIへ持ち込まないことを、プロジェクトの非交渉事項として定めています（[roadmap.md](roadmap.md) 参照）。

## 参加して何に触れられるか

- [x] **Rust** — 業務ロジック・認可・トランザクションの実装
- [x] **TypeScript / Next.js** — サーバーサイド統合を含むUI実装
- [x] **PostgreSQL（Supabase）** — スキーマ設計、Row Level Security、権限モデル
- [x] **契約優先のAPI設計** — OpenAPI起点の型生成とdrift検査
- [x] **データ移行・検証設計** — 段階移行のための突合方法
- [x] **CI/CD・デプロイ構成**
- [x] **AIエージェント運用** — 開発プロセスへの組み込み（[development-approach.md](development-approach.md) 参照）
