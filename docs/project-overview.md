# プロジェクト概要

## 何を作っているか

社内で過去に利用していた業務システムを、ゼロから設計し直しています。対象領域はメンバー管理を中心に、経歴・スキル、現場・案件、面談、人事考課、権限管理まで広がる、いわゆる基幹寄りの社内システムです。

旧システムは単一ページアプリケーションのフロントエンドと、サーバーサイドAPI、リレーショナルデータベースを中心に構成されています。これを Next.js / Rust / Supabase を中心とした構成へ、段階的に置き換えています。技術スタックの詳細は [architecture.md](architecture.md) を参照してください。

## なぜ作り直すか

一括で書き直すのではなく、機能単位の縦切りで移行しています。理由は次の通りです。

- 旧システムには自動テストがほとんど存在せず、既存挙動を保証する基準がありません。挙動の同等性を機能ごとに個別に検証しながら進める必要があります。
- 認可は単純な「管理者/一般」のようなロールモデルではなく、グループ・ユーザー単位の例外を組み合わせた、機能・操作単位の確認を必要とする独自モデルです。安易にロールへ縮約すると権限漏れが起きます。
- 起動・デプロイに必要な設定の一部が構成管理の外にあり、クリーンチェックアウトだけでは旧システムの手順を再現できません。

これらの制約から、「大きく作り直して一度に切り替える」方式は採らず、検証可能な最小単位（縦切り）で機能を移行し、各段階で旧システムとの結果差分を説明できる状態を維持する方針にしています。詳しい進め方は [development-approach.md](development-approach.md) を参照してください。

## 難しさ

このプロジェクトが技術的に歯応えがあると考えている点です。

- **認可モデルの移行**: グループ・ユーザー単位の例外を含む独自の認可モデルを、データベースの制約とクエリレベルの絞り込みとして再現する必要があります。アプリケーション層の判定だけに頼らない設計を重視しています。
- **データ移行の検証**: 自動テストがほとんど存在しない旧システムに対して、行数・チェックサム・キー関係の突合など、実データを見ずに移行の正しさを検証する方法を設計する必要があります。
- **保証基準がない状態からのテスト設計**: 「今まで動いていたから正しい」という前提が使えないため、機能ごとに期待される挙動を明文化してからテストを書く必要があります。

## 参加して何に触れられるか

- Rust による業務ロジック・認可・トランザクションの実装
- TypeScript / Next.js によるサーバーサイド統合を含むUI実装
- PostgreSQL（Supabase）でのスキーマ設計、Row Level Security、権限モデル
- 契約優先のAPI設計（OpenAPI起点の型生成とdrift検査）
- 段階移行のためのデータ移行・検証設計
- CI/CD、デプロイ構成の設計
- AIエージェントを開発プロセスへ組み込む運用（[development-approach.md](development-approach.md) 参照）
